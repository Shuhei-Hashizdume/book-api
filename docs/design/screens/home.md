# BookAPP — ホーム画面設計書

- **設計書のリポジトリ内保存先:** `docs/design/screens/home.md`
- **対象:** ホーム画面（PC・スマートフォン）
- **仕様基準日:** 2026-10-20
- **状態:** 画面仕様確定版。技術上の未実装事項・要確認事項は明確に分離する。
- **本書の範囲:** ホーム画面の情報構造・表示内容・操作・遷移・状態・APIとの対応。共通ビジュアルデザインは別途定義する。

> **仕様の読み方:** 「確定仕様」は画面の決定事項、「技術確認事項」は実装上の確認対象を示す。既存コードとの差分は画面仕様の変更を意味しない。図の `[表紙]` は表紙画像を示し、画像取得不可時には代替表示とする。

## 1. 目的と位置付け

BookAPPは、読みたい本や読書中・読了した本を管理し、読書で得た「気づき」を記録し、他ユーザーの公開おすすめ投稿から新しい本に出会うためのアプリ。ホームは次の3つの機能を1画面に集約する。

1. **読書中の本:** 自分が現在読んでいる本をすぐ確認し、詳細へ移動する。
2. **気づき登録:** 自分が登録した本を選び、読書中の学びを素早く保存する。
3. **新着投稿:** 全ユーザーの公開読了投稿を新着順で最大3件閲覧し、発見の入口とする。

「気づき」の登録は**自分用の記録**であり、公開読了投稿の作成とは別機能。気づき登録で公開投稿を自動作成しない。

## 3. 全体レイアウト・共通ナビゲーション【確定】

### 3.1 PC

- 上部ヘッダー左に `BookAPP`（押すとホーム）。ログイン済みなら右に `ユーザー名 ▼`、展開項目は `マイページ` / `ログアウト`。
- 左サイドバーは `ホーム` / `本棚` / `気づき` / `タイムライン` / `マイページ`。
- メインコンテンツは **読書中の本 → 気づき登録 → 新着投稿** の縦並び。各セクションは独立したカード領域。
- ゲストのヘッダー右は `[ログイン] [新規登録]`。ゲストでもサイドバーの項目は見える。

### 3.2 スマートフォン

- 上部に `BookAPP` とログイン済みの `[👤 ▼]`。タップ時の項目はPCと同じ。
- 下部ナビは `ホーム / 本棚 / 気づき / 投稿 / マイ` の5項目（表示ラベル）。`投稿` はタイムラインへの入口、`マイ` はマイページへの入口として扱う。正式なURL・画面名の統一は画面横断設計で整合させる。
- コンテンツはPCと同じ順番で縦積み。横幅に合わせカード内の要素を折り返す。
- ゲストの上部は `[ログイン] [登録]`。下部5ナビも表示し、保護画面への移動はログイン案内を経由する。

### 3.3 画面間の共通動作

- `BookAPP` のタップ／クリックはホームへ。
- ログアウトは確認ダイアログなしで実行し、**ウェルカム画面**へ移動。
- ゲストが `本棚`・`気づき`・`マイページ` など認証必須の画面へ移動すると、共通のログイン必要案内（ログイン／新規登録／戻る）を表示する。ログイン成功後は**元々要求した画面**に戻る。
- ホームと公開タイムラインのおすすめ投稿はゲストも閲覧可能。公開プロフィールも閲覧可能。フォロー操作にはログインが必要。
- 戻る／再訪／再読み込みでホームデータを再取得し、表示開始位置はページ上部。定期ポーリングは行わない。
- 入力途中の画面離脱確認は第7節に従う。

## 4. 読書中の本セクション【確定】

### 4.1 表示

- 現在のユーザーの登録本のうち、読書状態が `READING` の本を**全件**表示。
- 表示順は**ユーザーがその本を登録した日時の新しい順**（本そのものの作成日時ではない）。
- PC・スマホとも、表紙とタイトルのセットを**横方向にスクロール**して全件にアクセスできる。
- 表紙・タイトルはそれぞれその本の**本詳細画面**へのリンク。表紙がない・読み込めない場合も代替表示とタイトルで利用可能。
- セクション内に `[本棚を見る →]` を表示し、本人の本棚画面へ移動する。
- このセクションは読書状態の変更フォームではない。

### 4.2 読書中0冊

次の文言を表示する（改変しない）。

> 現在、読書中の本はありません。  
> 本棚から本を選んで、読書を始めましょう！
>
> [本棚を見る]

登録本が読みたい本や読了本として存在する場合、**気づき登録フォームは引き続き使用できる**。

### 4.3 ゲスト

本人の本一覧は取得しない。セクション内にログイン／新規登録の案内を表示し、ログイン後に利用できることを伝える。

## 5. 気づき登録セクション【確定】

### 5.1 フォーム構成

- 見出し `気づき登録`。
- 対象本選択欄 `[本を選択する ▼]`。選択済みなら選択した本の**表紙＋タイトル**を表示。
- 気づき本文のテキストエリア。
- 文字数表示 `N / 1000`（入力に追随）。
- `[登録する]` ボタン。
- 本選択、本文入力、登録結果表示は**ホーム内で完結**し、専用の登録画面へ遷移しない。

### 5.2 本選択一覧

- 候補は**本人が現在アカウントに登録している全書籍**。状態 `WANT_TO_READ`（読みたい）／`READING`（読書中）／`COMPLETED`（読了）のすべてを含む。他人の本、未登録の検索結果、削除済みの登録は含まない。
- **検索欄は置かない。読書状態のラベルも置かない。状態別タブも置かない。**
- 各行は**表紙＋タイトルのみ**。著者、ジャンル、状態、優先度、評価などは候補行に追加しない。
- 本人の登録日時が新しい順。候補数が多い場合は**展開パネル内部のみスクロール**できる。
- `[本を選択する]` を押すとフォーム内で**インライン展開**。別ページ・モーダル・画面全面の選択UIにはしない。
- 候補を選ぶと選択本を更新し、パネルを閉じる。選択中の表紙・タイトルを閉じた欄に表示する。
- **選択本を変更しても、入力済み本文と文字数を保持**する。確認ダイアログや変更通知は不要。パネルの開閉・内部スクロールでも本文を保持する。
- 選択だけではAPIへの気づき登録POSTを送信しない。選択行から本詳細へ遷移しない。
- 初期選択は、**読書中の本がちょうど1冊のときだけ、その1冊を自動選択**。読書中0冊または2冊以上なら未選択で開始する。登録本全体が1冊でも、その本が読書中でなければ自動選択しない。
- ユーザーが手動で選んだ本を、後続の取得結果によって不用意に上書きしない。
- APIへ送るのは**Bookの `id`**。`UserBook` レコードの `id` ではない。

### 5.3 入力制約とボタン

- 本文は**1〜1000文字**。空文字・空白のみは無効。前後空白除去後の内容が空なら送信不可。
- 1000文字を超える入力は受け付けない（貼り付けを含む）。カウンターは `N / 1000`。
- 登録ボタンは **本が選択済み・本文が有効・送信中でない** のすべてを満たすときだけ有効。
- 本人の登録本の取得が終わるまでは本選択・送信を有効にしない。
- 送信中は二重送信を防止する。リクエスト結果が不明な通信障害では自動再送しない。
- フロントとAPIの文字数判定は一致させる必要がある。絵文字・結合文字等の数え方は実装時に仕様整合を確認する（第11節）。

### 5.4 登録成功

- `POST /users/me/books/{book_id}/insights` 成功後も**ホームに留まる**。
- **本文だけクリア**し、文字数を `0 / 1000` に戻す。
- **選択した本はそのまま保持**する。
- フォーム内に **`✓ 気づきを登録しました！`** を表示し、**3秒後に消す**。
- 成功時に新着公開投稿を増やしたり、公開読了投稿を自動作成したりしない。

### 5.5 登録失敗

- 選択した本・入力本文・文字数を保持する。
- フォーム内に **`⚠ 登録できませんでした。もう一度お試しください。`** を表示。
- エラー表示は**時間経過で消さない**。本文編集または次の登録成功で消す。
- 認証401、対象本404、バリデーション422、通信断・タイムアウト・5xx等は共通エラー方針に従い、必要な場合は具体的な案内を追加する。結果不明のPOSTを自動的に繰り返さない。
- 成功通知と失敗通知を同時に残さない。

### 5.6 登録済みの本が0冊

**フォームを表示せず**、次の文言と導線を表示する（改変しない）。

> まだ本棚に本がありません。  
> 本を登録して、気づきを記録しましょう！
>
> [本を探して登録する →]

`本を探して登録する` は書籍検索・登録の導線へ移動。**本選択パネルに検索機能を追加する意味ではない**。

### 5.7 ゲスト

本人の候補本APIを呼ばず、入力フォームを表示しない。セクション内にログイン／新規登録の案内を表示する。

## 6. 新着投稿セクション【確定】

- 見出し `新着投稿`。
- **全ユーザーの公開読了投稿**を新着順で最大3件。フォロー中に限定しない。非公開投稿を含めない。
- 投稿カードは縦方向に並べる。各カードに**投稿者ユーザー名、本の表紙、本タイトル、★1〜5のおすすめ度、おすすめ理由**を表示。
- **カードの背景・余白・枠・おすすめ理由本文をクリックしても遷移しない。投稿詳細画面も設けない。**
- **投稿者ユーザー名**は公開プロフィールへのリンク。**本の表紙とタイトル**は本詳細へのリンク。
- おすすめ理由はPC・スマホとも**表示上3行まで**。3行を超える場合に限り `[詳細を見る ▼]` を表示し、同じカード内で全文を展開。展開時は `[閉じる ▲]` で3行へ戻せる。3行以下なら展開ボタンを表示しない。
- 文字数固定の省略ではなく**実際の表示行数**に基づく。PCとスマホでは行数が異なる場合がある。
- セクション末尾に `[投稿をもっと見る →]` を表示。**タイムラインの「おすすめ」タブ**へ移動する。
- ゲストも閲覧でき、投稿者の公開プロフィール・本詳細に移動できる。フォロー操作はログイン必須。

### 6.1 公開投稿0件

次の文言を表示する（改変しない）。

> まだ公開された投稿はありません。  
> 読了した本の感想を投稿して、おすすめの本を共有しよう！
>
> [タイムラインを見る]

ボタンは公開投稿0件でも**タイムラインの「おすすめ」タブ**へ移動する。

## 7. 非同期読み込み・エラー・離脱【確定】

### 7.1 読み込みと再取得

- 読書中の本、気づきフォームの候補本、新着投稿は**それぞれ独立して読み込み・エラー表示・再試行**できる。他セクションが失敗しても取得済みセクションは機能する。
- 候補本取得中は本選択と送信を無効化。候補の取得失敗を「登録本0冊」と表示しない。
- 読書中一覧の取得失敗を「読書中0冊」と表示しない。公開投稿取得失敗を「投稿0件」と表示しない。
- エラー表示は該当セクション内。`[再試行]` は原則として**そのセクションの取得処理のみ**再実行する。
- 認証状態が未確認の場合は本人データを先に描画しない。認証確認の通信障害をゲストと断定しない。共通認証設計 `docs/design/flows/authentication.md` を参照する。
- ページ再訪・リロード時にデータ再取得し、スクロール位置はページ上部。ポーリングなし。

### 7.2 未保存本文がある場合の画面離脱

- フォームに**未保存の本文が1文字以上ある状態**で、アプリ内の別画面へ移動しようとした場合、確認を表示する。
- ボタンは `[入力を続ける]` と `[移動する]`。前者は画面・本選択・本文を保持。後者は本文を破棄して指定先へ移動。
- 本選択の開閉・変更、理由の展開・折りたたみなど**ホーム内操作**では離脱確認しない。
- 本文が空、または保存成功後にクリア済みなら離脱確認しない。
- ブラウザの再読み込み・タブを閉じる操作には、利用可能な環境で**ブラウザ標準の `beforeunload` 確認**を使用する。ブラウザにより表示文言・挙動は異なるため独自文言の表示を保証しない。
- 確認のために別ページへ先に遷移してはいけない。

## 10. 既存バックエンドAPIと画面の対応

> 下記は2026-10-20時点のコード調査結果に基づく。稼働中のAPIの動作検証結果ではない。

| 用途 | 既存API・データ | ホーム側の利用方法／差分 |
|---|---|---|
| 本人情報・認証確認 | `GET /users/me`（現在Bearer） | 認証状態確定後に本人領域表示。Cookie移行は共通認証設計の別タスク |
| 本人の未読・読書中 | `GET /users/me/books?list_type=want_to_read` | `status=READING` を抽出して読書中に表示。読了済みはこの取得だけでは含まない |
| 本人の読了済み | `GET /users/me/books?list_type=completed` | 上記と合わせて気づき候補の全登録本を構成 |
| 候補データ | `UserBookListItem.book`（`id`, `title`, `cover_image_url` 等）、外側に `status` | 表示は表紙＋タイトルのみ。初期選択判定には `status` を利用 |
| 登録日時 | `UserBook` に `created_at` なし、一覧の日時ソート保証なし | **登録日時降順を実現する追加実装が必要**。ID降順で代用しない |
| 気づき保存 | `POST /users/me/books/{book_id}/insights`、JSON `{ "content": "..." }` | 選択した `Book.id` で保存。成功201。未登録本なら404 |
| 気づき本文 | `InsightCreate` / `InsightUpdate` に前後空白除去・min_length=1 | API側 `max_length=1000` の追加・既存データの確認が必要 |
| 公開新着投稿 | `GET /timeline/recommended`（認証不要・公開投稿・created_at降順） | 新着先頭3件を表示。現APIにlimit引数があると仮定しない |
| 公開投稿データ | `reading_post_id`, `user_id`, `username`, `book_id`, `title`, `recommendation_score`, `recommendation_reason`, `created_at`, `cover_image_url` | 投稿カードに必要な基本項目あり。理由3行判定はフロント表示処理 |
| フォロー中 | `GET /timeline/following`（認証必須） | **ホームの新着投稿には使用しない** |
| 本詳細 | `GET /books/{book_id}`、`GET /users/me/books/{book_id}` | ゲスト／本人で利用可能な詳細画面の契約に従って遷移 |
| 公開プロフィール | `GET /users/{user_id}/profile` | 投稿者ユーザー名から遷移 |
| 書籍検索 | `GET /books/search` | 登録本0冊の「本を探して登録する」導線。選択パネルには組み込まない |
| AI提案 | `POST /users/me/books/{book_id}/insights/{insight_id}/ai-suggestion` | ホームの気づき登録時には自動実行しない |

### 10.1 データの流れ

```text
認証確認 ──→ ログイン済み ──┬──→ 本人登録本（未読＋読書中） ──┐
                           │                                ├──→ 全登録本の統合
                           ├──→ 本人登録本（読了済み） ──────┘       │
                           │                                       ├─ status=READING → 読書中の本
                           │                                       └─ 登録日時降順 → 本選択候補
                           │                                                            │
                           │                                                   選択 Book.id + content
                           │                                                            ↓
                           │                                      POST /users/me/books/{book_id}/insights
                           │                                                            │
                           │                                              成功（本文クリア）/失敗（保持）
                           │
公開（ゲストも可） ──────────┴──→ GET /timeline/recommended → 公開新着最大3件
                                                               └→ 3行超の理由をインライン展開
```

- 2種類の本人一覧の片方だけ取得できた場合は、取得済みの一部を「全登録本」と誤認しない。
- `UserBook` の登録日時追加に伴う既存レコードの過去日時は、元データから正確には復元できない。移行方針は実装前に確認する。
- 公開新着APIが全件を返す場合、画面で先頭3件に絞る方法とAPI側に件数制限を追加する方法は、性能・既存契約を踏まえて実装段階で決定する。**画面上の最大3件は確定**。
