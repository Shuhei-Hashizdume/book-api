# user-profile.md

# BookAPP — 他ユーザープロフィール画面 仕様書

## 1. 画面の目的

他ユーザーの基本プロフィールと公開された読了投稿を閲覧し、フォローや新しい本の発見につなげる画面。

BookAPPのサービス目的である「他ユーザーのおすすめから新しい本と出会う」を実現する。

本画面は、他ユーザーの読書活動をすべて公開する画面ではなく、**公開読了投稿を中心としたシンプルなプロフィール画面**とする。

## 2. 設計の確定事項

設計①〜⑮の決定内容は以下のとおり。

| No. | 項目                   | 確定仕様                                       |
| --- | ---------------------- | ---------------------------------------------- |
| ①   | 画面の基本構成         | 公開読了投稿を中心とするシンプルなプロフィール |
| ②   | 投稿の表示形式         | タイムラインと同じカード形式                   |
| ③   | 読んだ本の冊数         | 表示のみ。タップ不可                           |
| ④   | フォロー操作           | 確認ダイアログなしで切り替え                   |
| ⑤   | フォロー関係           | 人数タップでフォロー中・フォロワー一覧へ       |
| ⑥   | 投稿の並び順           | 新しい投稿順                                   |
| ⑦   | 追加読み込み           | 20件ずつ無限スクロール                         |
| ⑧   | 投稿0件                | 案内メッセージのみ                             |
| ⑨   | 自分自身のプロフィール | マイページへ移動                               |
| ⑩   | 戻る操作               | 元画面・タブ・スクロール・取得済みデータを維持 |
| ⑪   | 読み込み・エラー       | スケルトン、部分エラー、再試行                 |
| ⑫   | PC・スマホ             | 共通の1カラム。PC最大幅600px                   |
| ⑬   | 本のタップ             | 表紙・タイトルから書籍詳細へ                   |
| ⑭   | 非公開・削除投稿       | 再取得時に一覧から除外                         |
| ⑮   | 再訪問時の更新         | キャッシュを先に表示し、裏側で再取得           |

## 3. 表示対象とプライバシー

### 3.1 表示する情報

- ユーザーアイコン
- ユーザー名
- 自己紹介文（設定されている場合）
- フォロー中の人数
- フォロワーの人数
- フォロー状態に応じたボタン
- 「📚 読んだ本 ○冊」
- 公開されている読了投稿

アイコンはマイページで定義した共通の動物アイコンを使用する。アイコン未設定時は共通のデフォルトアイコンを表示する。

### 3.2 表示しない情報

- 他ユーザーの読書記録一覧
- 読書状態の一覧
- 読みたい本リスト
- 気づき一覧
- 非公開の読了投稿
- 非公開投稿の件数や存在を示す情報
- プロフィール編集ボタン
- マイページ専用の3タブ

他ユーザーのプロフィールでは「読書記録／読了投稿／気づき」のタブを表示しない。

### 3.3 読んだ本の冊数

表示形式は以下とする。

`📚 読んだ本 24冊`

- マイページと同じ冊数の定義を使用する。
- 同じ本を重複カウントしない。
- 冊数はタップできない。
- 読んだ本の一覧画面へは移動しない。

**実装確認事項：** 現行バックエンドの読了冊数の集計方法を確認し、マイページと公開プロフィールで同じ意味の数値になることを確認する。集計元テーブルや履歴の扱いは実コードに基づいて判断する。

## 5. プロフィール情報

### 5.1 ユーザーアイコン

- マイページと同じアイコンコンポーネントを使用する。
- ユーザーが設定した動物アイコンを表示する。
- 未設定の場合はデフォルトの本アイコンを表示する。
- この画面からアイコンは変更できない。

### 5.2 ユーザー名

- 対象ユーザーの現在のユーザー名を表示する。
- 内部のユーザー識別には変更可能なユーザー名ではなく、安定したユーザーIDを使用する。
- この画面からユーザー名は編集できない。

### 5.3 自己紹介文

- 自己紹介文が設定されている場合に表示する。
- 未設定の場合は自己紹介欄を省略する。
- 入力・編集機能は設けない。
- 改行を含む場合は適切に表示する。
- 長文や長い単語でも画面の横幅を超えないようにする。

自己紹介の入力上限や保存方法は、マイページのプロフィール編集仕様に従う。

## 6. フォロー機能

### 6.1 フォローボタン

対象ユーザーをフォローしていない場合：

`[フォローする]`

フォロー済みの場合：

`[フォロー中 ✓]`

ボタンをタップした場合は以下の動作とする。

```text
[フォローする]
       │
       │ タップ
       ▼
  フォローAPI実行
       │
       ├─ 成功 → [フォロー中 ✓]
       │           フォロワー数を更新
       │
       └─ 失敗 → 元の表示を維持・復元
                   エラーを通知
```

フォロー解除も同様とする。

- フォロー・解除時の確認ダイアログは表示しない。
- 通信中は二重操作を防止する。
- 成功時はボタンとフォロワー数を同期する。
- 失敗時はボタンと人数を正しい状態に戻す。
- 他の画面で表示されている同じユーザーのフォロー状態にも、可能な範囲で変更を反映する。

通信完了前に表示を切り替える楽観的更新を採用する場合は、失敗時のロールバックを必須とする。楽観的更新か成功後更新かの内部方式は、既存の共通実装を確認して統一する。

### 6.2 フォロー中・フォロワー人数

両方の人数をタップ可能とする。

```text
┌──────────────────────────────┐
│ フォロー中 32  フォロワー 18 │
└──────────────────────────────┘
       │               │
       ▼               ▼
 フォロー中一覧   フォロワー一覧
```

- フォロー中をタップすると、対象ユーザーがフォローしている人の一覧を開く。
- フォロワーをタップすると、対象ユーザーをフォローしている人の一覧を開く。
- マイページで定義した共通のフォロー一覧画面を再利用する。
- 遷移時に対象ユーザーIDと初期タブを渡す。
- 一覧内のフォローボタンは、ログイン中の自分から見たフォロー状態を表示する。
- 一覧内のユーザーをタップすると、そのユーザーのプロフィールへ移動する。
- 自分自身をタップした場合はマイページへ移動する。

### 6.3 自分自身へのフォロー禁止

ログイン中のユーザーとプロフィール対象のユーザーIDが一致する場合は、公開プロフィールではなくマイページへ移動する。

フロントエンドでの制御に加え、バックエンドでも自分自身へのフォローを禁止する。

## 7. 公開読了投稿

### 7.1 表示対象

以下の条件を満たす読了投稿のみを表示する。

- 投稿者がプロフィール対象ユーザーである。
- 公開状態が公開である。
- 削除されていない投稿である。

非公開投稿は一覧取得APIのレスポンスに含めない。

フロントエンドで受信後に非公開投稿を隠す方式だけに依存しない。

### 7.2 カードの表示形式

タイムラインと同じ投稿カードコンポーネントを使用する。

表示項目：

- 投稿者のアイコン
- 投稿者のユーザー名
- 本の表紙
- 本のタイトル
- 本の著者
- おすすめ度（星1〜5）
- おすすめ理由
- いいね数といいね状態
- 投稿日

表示形式・おすすめ理由の省略・日付表記・いいね操作は、既存の `timeline.md` および `post-detail.md` の共通仕様に従う。

プロフィール専用に別デザインの投稿カードを新規作成しない。

### 7.3 投稿の並び順

新しい投稿順とする。

- `created_at` の降順を基本とする。
- 投稿日が同じ場合でも順序が安定するよう、一意なIDを第2ソートキーに使用する。
- おすすめ度順の並び替えは設けない。
- 並び替えボタンやフィルターは設けない。

### 7.4 投稿カード内の操作

```text
┌──────────────────────────────┐
│ 🐻 ユーザーA                │ → プロフィール
│                              │
│ 📖 本A / 著者A              │ → 書籍詳細
│                              │
│ ⭐⭐⭐⭐⭐                   │
│ おすすめ理由の文章...       │ → 投稿詳細
│                              │
│ ♡ 12                        │ → いいね操作
└──────────────────────────────┘
```

- 投稿者の名前・アイコン：プロフィール画面へ移動
- 本の表紙・タイトル：書籍詳細画面へ移動
- 投稿カードのその他の詳細表示領域：投稿詳細画面へ移動
- いいね操作：タイムラインの共通仕様に従う

カード内のリンク・ボタンをタップした際、親カードのクリック処理が重複して実行されないようにする。

プロフィール対象のユーザー名を再度タップした場合は、同じプロフィール画面を不要に積み重ねないようにする。

## 8. 投稿の追加読み込み

### 8.1 基本仕様

- 初回取得：20件
- 追加取得：20件
- 取得方式：無限スクロール
- ページネーション：カーソル方式を基本とする
- 投稿順：新しい投稿順

```text
投稿1〜20を表示
       │
       │ 下へスクロール
       ▼
投稿21〜40を追加取得
       │
       │ 下へスクロール
       ▼
投稿41〜60を追加取得
       │
       ▼
   最終ページ
       │
       ▼
追加読み込み終了
```

### 8.2 読み込み制御

- 一度に複数の追加取得を実行しない。
- 同じカーソルの重複リクエストを防ぐ。
- 取得済みの投稿IDが重複しないようにする。
- 次のページがない場合は追加取得を停止する。
- 追加取得に失敗しても、取得済みの投稿は保持する。
- 追加取得失敗時は、その位置から再試行できるようにする。
- 途中で新しい投稿が作成されても、ページ境界で重複や取りこぼしが起きにくい方式を使用する。

## 9. 投稿が0件の場合

公開読了投稿が存在しない場合は、以下の表示とする。

```text
┌──────────────────────────────┐
│ 公開された読了投稿           │
│                              │
│             📖               │
│                              │
│ まだ公開された投稿は         │
│ ありません                   │
│                              │
└──────────────────────────────┘
```

- 投稿がない理由は表示しない。
- 非公開投稿が存在するかどうかを示さない。
- タイムラインへの誘導ボタンは設置しない。
- プロフィール情報とフォローボタンは通常どおり表示する。

## 10. 画面遷移

### 10.1 画面への入口

想定する入口：

- タイムラインの投稿者名・アイコン
- 投稿詳細の投稿者名・アイコン
- フォロー中一覧
- フォロワー一覧
- その他、ユーザーを表示する共通コンポーネント

入口ごとに別のプロフィール画面を作成せず、共通の `user-profile` 画面へ遷移する。

### 10.2 ユーザーIDによる振り分け

```text
ユーザー名・アイコンをタップ
             │
             ▼
     対象ユーザーIDを取得
             │
             ▼
    自分自身のユーザーID？
         │           │
        YES          NO
         │           │
         ▼           ▼
     マイページ   他ユーザーの
                  プロフィール
```

ユーザー名の文字列比較ではなく、ユーザーIDで判定する。

### 10.3 プロフィールからの移動

```text
          他ユーザープロフィール
                    │
        ┌───────────┼────────────┐
        │           │            │
        ▼           ▼            ▼
  フォロー一覧   投稿詳細     書籍詳細
        │           │            │
        └───────────┴────────────┘
                    │
                   戻る
                    ▼
          元のプロフィール状態
```

### 10.4 戻る操作

他ユーザープロフィールから戻った場合：

- 元の画面に戻る。
- 元のタブを維持する。
- 元のスクロール位置を維持する。
- 取得済みデータを維持する。
- 必要な変更だけ表示に反映する。

また、プロフィールから投稿詳細や書籍詳細へ移動し、戻ってきた場合も、プロフィールのスクロール位置と取得済み投稿を復元する。

再取得を行っても、不必要に一覧の先頭へ戻さない。

## 11. 読み込み状態・エラー表示

### 11.1 初回読み込み

初回アクセス時にキャッシュがない場合は、スケルトンを表示する。

```text
┌──────────────────────────────┐
│ ← 戻る                       │
│                              │
│ ◯  ▰▰▰▰▰                  │
│     ▰▰▰▰▰▰▰               │
│                              │
│ ▰▰▰▰    ▰▰▰▰             │
│                              │
│ [ ▰▰▰▰▰▰▰▰▰▰ ]          │
│                              │
│ ▰▰▰▰▰▰▰▰                │
├──────────────────────────────┤
│ ▰▰▰▰▰▰▰▰                │
│ ▰▰▰▰▰▰▰▰                │
└──────────────────────────────┘
```

実際のスケルトンは、プロフィールと投稿カードの配置に近い形とする。

### 11.2 プロフィール取得失敗

プロフィール情報の取得に失敗し、表示可能なキャッシュもない場合：

```text
┌──────────────────────────────┐
│ ← 戻る                       │
│                              │
│ プロフィールを               │
│ 読み込めませんでした         │
│                              │
│      [再読み込み]            │
└──────────────────────────────┘
```

再読み込みボタンから取得を再試行できるようにする。

### 11.3 投稿一覧のみ取得失敗

プロフィール情報は維持する。

```text
┌──────────────────────────────┐
│ 🐻 ユーザーA                │
│ フォロー中 32               │
│ フォロワー 18               │
│ [フォローする]              │
│                              │
│ 📚 読んだ本 24冊            │
├──────────────────────────────┤
│ 公開された読了投稿           │
│                              │
│ 投稿を読み込めませんでした   │
│                              │
│      [再試行]                │
└──────────────────────────────┘
```

プロフィール取得と投稿一覧取得は、独立した読み込み・エラー状態として扱う。

### 11.4 ユーザーが存在しない場合

存在しないユーザーIDや閲覧できないユーザーの場合は、通常の通信エラーとは区別する。

表示例：

`ユーザーが見つかりません`

戻る操作を提供する。

認証切れの場合は、アプリ共通の認証エラー処理に従う。

## 12. キャッシュと再取得

### 12.1 初回アクセス

- キャッシュがなければスケルトンを表示する。
- APIからプロフィールと公開読了投稿を取得する。
- 取得に成功した情報を表示する。

### 12.2 再訪問

キャッシュがある場合は、前回取得したデータを先に表示し、裏側で最新情報を取得する。

この方式は一般に **Stale-While-Revalidate（SWR）** と呼ばれる。

```text
プロフィールへ再訪問
          │
          ▼
   キャッシュがある？
      │         │
     YES        NO
      │         │
      ▼         ▼
  前回データ   スケルトン
  を表示       を表示
      │         │
      └────┬────┘
           ▼
      APIから再取得
           │
      ┌────┴────┐
      │         │
     成功       失敗
      │         │
      ▼         ▼
  最新データ   表示可能な
  に更新       データを維持
```

### 12.3 更新対象

再取得に成功した場合、必要に応じて以下を更新する。

- ユーザー名
- アイコン
- 自己紹介文
- フォロー中人数
- フォロワー人数
- 自分のフォロー状態
- 読んだ本の冊数
- 公開読了投稿一覧

### 12.4 スクロール位置との整合性

別画面から「戻る」操作でプロフィールへ復帰する場合、設計⑩のスクロール復元を優先する。

- 取得済みページを不用意に破棄しない。
- 再取得でスクロール位置を強制的に先頭へ戻さない。
- 投稿の増減があっても、可能な限り閲覧位置を維持する。
- 明示的に新しくプロフィールを開く場合と、戻る操作による復帰を区別する。

### 12.5 キャッシュの安全性

キャッシュは表示速度の改善を目的とする。

- キャッシュの存在を閲覧権限の証明として扱わない。
- 投稿詳細の取得時にはサーバー側で公開権限を確認する。
- 非公開化・削除を把握した投稿はキャッシュから除外する。
- ログアウトやアカウント切り替え時には、ユーザー固有のキャッシュを適切に無効化する。
- 古いキャッシュが原因で、非公開投稿を新たに閲覧できる状態にしてはならない。

## 13. 投稿の非公開化・削除

### 13.1 一覧表示

投稿が非公開に変更された場合、次の正常な再取得時に一覧から除外する。

投稿が削除された場合も同様とする。

```text
再取得前：

[投稿A]
[投稿B]
[投稿C]

投稿Bが非公開化
        │
        ▼
最新データを再取得
        │
        ▼
[投稿A]
[投稿C]
```

### 13.2 投稿詳細へのアクセス

非公開化・削除済みの投稿に、古いリンクやカードからアクセスした場合：

- 他ユーザーには投稿内容を返さない。
- サーバー側で公開状態とアクセス権限を確認する。
- 閲覧できない場合は、投稿詳細の共通仕様に従ってエラー表示する。
- 非公開投稿の存在を不要に推測できる情報を返さない。

### 13.3 常時監視について

投稿の変更をリアルタイムに監視する仕組みは、本画面の必須要件としない。

再訪問やデータ再取得のタイミングで最新状態を反映する。

## 14. 既存画面との共通化

次の仕様・コンポーネントとの整合性を保つ。

| 既存仕様書       | 再利用・統一する内容                               |
| ---------------- | -------------------------------------------------- |
| `mypage.md`      | アイコン、プロフィール情報、フォロー一覧、読了冊数 |
| `timeline.md`    | 読了投稿カード、いいね、20件単位の無限スクロール   |
| `post-detail.md` | 投稿詳細への遷移、公開権限、戻る操作               |
| `book-detail.md` | 書籍詳細への遷移                                   |
| `post-edit.md`   | 投稿の公開・非公開変更後の表示整合性               |

他ユーザープロフィール専用に同じ機能を重複実装することは避ける。

ただし、マイページでは自分の非公開投稿も閲覧できる一方、他ユーザープロフィールでは公開投稿だけを閲覧できる。この権限の違いを維持すること。

## 15. API・バックエンドの要件

### 15.1 必要なデータ・機能

本画面で必要となるデータ・機能は以下のとおり。

1. ユーザーIDを指定した公開プロフィール取得
2. ログイン中ユーザーから見たフォロー状態の取得
3. フォロー・フォロー解除
4. 対象ユーザーのフォロー中・フォロワー一覧取得
5. 対象ユーザーの公開読了投稿一覧取得
6. 公開読了投稿の20件単位・カーソル方式による取得
7. 公開プロフィールの読了冊数集計
8. 投稿詳細の閲覧権限チェック

既存APIで対応できる場合は再利用する。

### 15.2 公開プロフィール取得

対象ユーザーについて、少なくとも以下の情報を取得できること。

- ユーザーID
- ユーザー名
- アイコン
- 自己紹介文
- フォロー中人数
- フォロワー人数
- ログイン中ユーザーから見たフォロー状態
- 読了冊数

具体的なエンドポイント名・レスポンス形式は既存APIとの整合性を優先する。

### 15.3 公開読了投稿一覧取得

以下の条件を満たすこと。

- 対象ユーザーIDで絞り込める。
- 公開投稿だけを返す。
- 新しい投稿順で返す。
- 20件ずつ取得できる。
- 次のページを取得するためのカーソルを扱える。
- 投稿カード表示に必要な情報を取得できる。
- 非公開投稿・削除済み投稿を返さない。

### 15.4 読了冊数の整合性

マイページと公開プロフィールの「読んだ本 ○冊」は同じ集計ルールを使用する。

集計元となるデータや読了履歴の扱いは、既存のデータモデルと照合して整合性を保つ。

### 15.5 既存実装との差異

APIやDBの具体的な構造は本仕様書だけでは確定しない。

既存実装に必要な機能がない場合は、仕様との差分と影響範囲を確認したうえで対応方法を決定する。

## 16. テスト・受け入れ条件

### 16.1 プロフィール表示

- 他ユーザーのアイコン・名前・自己紹介が表示される。
- 自己紹介未設定でもレイアウトが崩れない。
- フォロー中・フォロワー人数が表示される。
- 読了冊数が表示され、タップしても遷移しない。
- 読書記録・気づき・非公開投稿が表示されない。

### 16.2 フォロー

- 未フォロー時に「フォローする」が表示される。
- フォロー成功後に「フォロー中」へ切り替わる。
- 解除成功後に「フォローする」へ戻る。
- フォロワー数が更新される。
- API失敗時に不正な状態が残らない。
- 通信中の連打で重複リクエストが発生しない。
- 自分自身をフォローできない。

### 16.3 フォロー一覧

- フォロー中人数から対象ユーザーのフォロー中一覧を開ける。
- フォロワー人数から対象ユーザーのフォロワー一覧を開ける。
- 一覧内のフォロー状態がログイン中の自分を基準に表示される。
- 一覧から別ユーザーのプロフィールへ移動できる。

### 16.4 公開読了投稿

- 対象ユーザーの公開投稿だけ表示される。
- 投稿日の新しい順で表示される。
- 最初の20件を取得できる。
- スクロールに応じて次の20件を取得できる。
- 同じ投稿が重複表示されない。
- 投稿0件の場合に指定メッセージが表示される。
- 本の表紙・タイトルから書籍詳細へ移動できる。
- 投稿カードから投稿詳細へ移動できる。
- いいね操作が共通仕様どおり動作する。

### 16.5 画面遷移・復元

- 自分自身のプロフィールへの遷移はマイページに振り分けられる。
- 戻る操作で元の画面に戻れる。
- 元のタブ・スクロール位置・取得済みデータを維持できる。
- プロフィールから投稿詳細へ移動して戻っても位置が維持される。
- 再訪問時にキャッシュがあれば先に表示できる。
- 裏側での再取得成功後に最新情報へ更新される。

### 16.6 エラー・セキュリティ

- 初回読み込み中にスケルトンが表示される。
- プロフィール取得失敗時に再試行できる。
- 投稿一覧だけ失敗した場合にプロフィール情報が残る。
- 追加読み込み失敗時に既存投稿が消えない。
- 存在しないユーザーに適切な案内を表示する。
- 非公開・削除された投稿が再取得後に一覧から消える。
- 非公開投稿のURLを直接指定しても他ユーザーが閲覧できない。
- ログアウト・アカウント切り替えで他アカウントの専用キャッシュが残らない。
