# 読了投稿編集画面 仕様書（post-edit.md）

- 対象: BookAPP / 読了投稿編集画面
- 状態: **画面設計15/15項目確定**
- 用途: Cursor / Codexへの実装引き継ぎ
- 注記: この文書は画面設計上の確定仕様を記載する。APIパス・既存ORM名・ルーティング・技術的な実現方法は、実装前にリポジトリで確認すること。

## 1. 目的・画面への導線

既存の読了投稿について、投稿者本人が「おすすめ度」「おすすめ理由」「公開設定」を編集するための画面。

```text
読了投稿詳細画面
    │ 投稿者本人のみ「…」→「編集する」
    ▼
読了投稿編集画面
    ├─ 保存成功 → 更新済みの読了投稿詳細画面（完了通知）
    ├─ 保存失敗 → 編集画面のまま入力保持（エラー表示）
    └─ 戻る     → 変更なし: 詳細へ / 変更あり: 破棄確認
```

- 投稿の編集は**投稿者本人のみ**許可する。UIの表示制御だけではなく、バックエンドで所有者を検証する。
- 編集対象の書籍そのものは変更できない。
- 保存完了まではDBを更新しない。

## 2. 確定した15項目

| No. | 項目 | 確定仕様 |
|---|---|---|
| ① | 編集対象 | おすすめ度・おすすめ理由・公開設定の3項目のみ。書籍は変更不可 |
| ② | 画面構成 | PC・スマホ共通で縦1列。書籍情報→おすすめ度→理由→公開設定→保存 |
| ③ | 書籍情報 | 表紙画像とタイトルのみ、読み取り専用。表紙なし/読み込み失敗時は `NO COVER` |
| ④ | おすすめ度 | ★1〜5のプルダウン（select）。現在値を初期選択。必須。保存前のDB更新なし |
| ⑤ | おすすめ理由 | 現在の理由を初期表示した固定高さの複数行テキストエリア。長文は入力欄内スクロール。改行保持 |
| ⑥ | 文字数 | 最大1,000文字。右下に `125 / 1000` 形式のリアルタイムカウンター。上限超過入力を拒否。フロント・バック両方で検証 |
| ⑦ | 公開設定 | 説明付きラジオボタン。公開＝他ユーザー閲覧可、非公開＝本人のみ。現在値を初期選択 |
| ⑧ | 保存ボタン | フォーム最下部。スクロールに追従させず、画面下部固定もしない |
| ⑨ | バリデーション | おすすめ度1〜5必須、理由1〜1,000文字必須・空白/改行のみ不可、公開/非公開必須。エラーは項目直下。新規投稿画面にも同一ルールを適用 |
| ⑩ | 変更なし | 初期状態では保存ボタン無効。1項目でも変更があれば、入力が有効な場合に限り有効。すべて元に戻せば無効。変更なしで保存APIを呼ばない |
| ⑪ | 未保存で戻る | 変更がある場合のみ破棄確認ダイアログ。「編集を続ける」は入力保持、「破棄して戻る」は保存せず詳細へ。変更なしは直接戻る。ブラウザ戻るも可能な範囲で対応 |
| ⑫ | 保存中 | ボタンを `◌ 保存中...` に変更。二重送信防止、入力項目操作不可、戻るボタン遷移防止。全画面オーバーレイは使用しない |
| ⑬ | 保存成功 | 投稿詳細へ戻り、更新値を反映。上部に `✓ 投稿を更新しました` を数秒間表示。非公開化した投稿は取得済みタイムライン一覧から除去。詳細から戻ると元の閲覧画面へ |
| ⑭ | 保存失敗 | 編集画面に留まり、入力をすべて保持。フォーム上部にエラーを表示。入力不正は項目直下にも表示。保存中状態を解除して再試行可能 |
| ⑮ | レスポンシブ | PCは最大幅600pxで中央配置。スマホは画面幅に合わせ可変。縦スクロール、保存ボタン固定なし |

## 5. 画面状態と操作フロー

### 5.1 初期表示

1. 対象投稿と書籍情報を取得し、投稿者本人の編集権限を確認する。
2. 3つの入力項目に既存値をセットする。
3. 初期値を変更比較の基準として保持する。
4. 変更がないため保存ボタンは無効。

### 5.2 編集・入力検証

- いずれかの値が初期値と異なり、すべての項目が有効な場合だけ保存可能。
- 理由が空、または空白・改行のみの場合は保存不可。
- 理由が1,000文字を超える入力は受け付けない。
- 項目エラーは該当欄の直下に表示。
- プルダウン、テキストエリア、ラジオボタンの変更は保存実行までローカル状態にとどめる。

### 5.3 未保存のまま戻る

```text
「← 戻る」
  ├─ 未変更 → 投稿詳細画面
  └─ 変更あり
       ▼
  ┌──────────────────────────┐
  │ 変更内容を破棄しますか？ │
  │ 保存していない変更は     │
  │ 失われます。             │
  │                          │
  │ [編集を続ける]           │ → ダイアログを閉じ、入力保持
  │ [破棄して戻る]           │ → 保存せず投稿詳細へ
  └──────────────────────────┘
```

ブラウザの戻る操作についても、実装可能な範囲で同じ破棄確認を適用する。ブラウザのタブ終了・リロード等で独自ダイアログが使えない場合の扱いは実装時に検討する。

### 5.4 保存中・成功・失敗

```text
[変更を保存] （変更あり・入力有効）
       │
       ▼
保存APIを1回実行
入力欄・戻る操作を無効化
ボタン表示: [◌ 保存中...]
       │
       ├─ 成功 → 更新後の投稿詳細画面
       │           ├─ ✓ 投稿を更新しました（数秒で消える）
       │           └─ 非公開化時は取得済みタイムラインから除去
       │
       └─ 失敗 → 編集画面に残る
                   ├─ 3項目の入力値を保持
                   ├─ 上部にエラー表示
                   ├─ 入力エラーは項目直下にも表示
                   └─ 操作を再有効化し、再試行可能
```

エラー表示例:

```text
⚠ 変更を保存できませんでした
通信状況を確認して、もう一度お試しください。
```

## 6. フロントエンド・バックエンドの責務

### フロントエンド

- 表紙・タイトルを読み取り専用で表示し、表紙欠損時は `NO COVER` を表示。
- 既存の投稿値をフォームに設定し、変更の有無を判定。
- ★1〜5のselect、固定高さtextarea、公開設定radioを提供。
- 文字数カウンター、1,000文字入力制限、必須・空白のみチェック、項目別エラー表示。
- 保存ボタンの有効/無効、保存中表示、二重送信防止、入力・戻る操作制限。
- 未保存変更の破棄確認、保存成功時の詳細画面遷移と一時通知。
- 保存失敗時の入力保持と再試行。
- 非公開化時のタイムラインキャッシュとの整合を取る。

### バックエンド（FastAPI側で担保すべき条件）

- 認証済みユーザーであること、および対象投稿の所有者であることを検証する。
- 更新できるフィールドをおすすめ度・理由・公開設定に限定する。書籍ID等の変更を認めない。
- おすすめ度1〜5、理由1〜1,000文字かつ空白・改行のみ不可、公開設定の妥当性を検証する。
- 更新成功時には、更新後の投稿情報をフロントエンドが反映できるようにする。
- 非公開投稿のアクセス制御は詳細画面やタイムライン側でも維持する（他ユーザーに公開しない）。
- エラー時にフロントエンドが入力不正と通信/サーバーエラーを区別できるようにする。

※ APIパス、HTTPメソッド、ステータスコード、レスポンス形式、データモデルの名称は**未確定**。既存コードとAPI設計を確認してから定義する。

## 7. 他画面との整合

- **読了投稿詳細画面:** 投稿者本人の「…」→「編集する」から遷移。保存後は同じ投稿の詳細へ戻り、最新の内容を表示。
- **タイムライン:** 非公開に切り替えた投稿は、閲覧権限のないユーザーの一覧に残さない。既に取得した一覧のキャッシュも整合させる。
- **読了投稿新規作成画面:** 理由必須（1〜1,000文字、空白・改行のみ不可）など、⑨で確定した入力規則を共通化する。

## 8. 確定事項と未決定・実装時確認事項

### 確定

- ①〜⑮の画面仕様すべて。
- 保存成功後は投稿詳細へ戻る。
- 投稿者本人以外の編集は認めない。

### 実装時に確認・決定（本書では勝手に確定しない）

- 実際のAPIエンドポイント、HTTPメソッド、リクエスト/レスポンス、ORMフィールド名。
- 初期データ取得中、投稿が削除済み・閲覧不可の場合の編集画面固有の表示（既存の詳細画面仕様との整合を優先）。
- 保存後の一時通知の具体的な表示秒数。
- 文字数のカウント基準（JavaScript文字列長とUnicodeコードポイント等の差）、前後空白の保存方針。**空白・改行のみ不可という確定条件は必ず維持する。**
- ブラウザの履歴操作・リロード・タブ終了時の破棄確認の技術的制約。
- ネットワーク切断やタイムアウトでサーバー側の更新成否が不明な場合の再試行・再取得方針。
- フォームの細かな余白・配色・フォント・アクセシビリティ属性。

## 9. Codexへの実装上の注意

1. 既存リポジトリの構成と認証・投稿詳細・タイムラインの仕様を先に確認する。
2. **確定仕様と未決定事項を混同しない。** 未決定のAPI構造やデータモデルを推測で確定しない。
3. 既存の設計と衝突する点は、実装前に質問する。
4. 一度に大量実装せず、目的→全体像→変更箇所と理由を説明し、理解確認を挟んで進める。
5. フロントエンドだけでなく、バックエンドの権限チェックと入力検証をテストする。
