# BookAPP 読了投稿詳細画面 仕様書

- ファイル名: `post-detail.md`
- 対象画面: 読了投稿詳細画面
- 状態: **画面設計20項目すべて確定**
- 用途: Cursor / Codexへの設計引き継ぎ
- 注意: 本書は**画面設計仕様**であり、記載したAPIや画面がすべて実装済みであることを意味しない。

## 1. 画面の目的

読了投稿のおすすめ度・おすすめ理由を全文で確認し、投稿者のプロフィールや書籍詳細へ移動できる画面。投稿者本人は投稿編集・削除・公開状態の確認ができ、他のユーザーは公開投稿へのいいね操作ができる。

## 2. 確定事項一覧（全20項目）

| No. | 項目 | 確定仕様 |
|---|---|---|
| ① | 基本レイアウト | タイムラインの投稿カードを拡張した一体型レイアウト |
| ② | 投稿者情報 | アバターなし、ユーザー名のみ。タップでそのユーザーのプロフィールへ移動 |
| ③ | 書籍情報 | 表紙＋タイトルのみ。どちらも書籍詳細へ移動。表紙なしはタイムラインと同じ `NO COVER` |
| ④ | おすすめ度 | 5つ星の視覚表示のみ（例 `★★★★☆`）。数値表記なし。詳細画面では編集不可 |
| ⑤ | おすすめ理由 | 全文を省略せず表示し、入力時の改行を保持。画面全体が自然に縦スクロール |
| ⑥ | 投稿日 | `YYYY/MM/DD`。時刻・相対日時なし |
| ⑦ | いいね | ハートと件数を一体の操作対象とする。0件は `♡` のみ。本人は自分の投稿にいいね不可 |
| ⑧ | 操作メニュー | 投稿者本人に限り右上に `…`。項目は「編集する」「削除する」 |
| ⑨ | 編集画面への遷移 | 「編集する」で専用の投稿編集画面へ。既存内容を初期表示し、保存成功後は投稿詳細へ戻る |
| ⑩ | 削除確認 | 「削除する」で確認ダイアログを表示。明示的な最終確認後のみ削除APIを実行 |
| ⑪ | 削除成功後 | 投稿詳細を開いた元の画面へ戻る。元の一覧から削除投稿を除外 |
| ⑫ | 公開状態表示 | 自分の投稿にだけ「公開中」「非公開」ラベルを表示。ラベルは表示専用 |
| ⑬ | 公開状態変更 | 専用の投稿編集画面でのみ変更し、保存する |
| ⑭ | 非公開投稿の閲覧 | 投稿者本人のみ。本人以外の詳細取得は原則404。公開タイムラインにも表示しない |
| ⑮ | 投稿不存在・閲覧不可 | 「投稿が見つかりません」＋説明＋「前の画面に戻る」。理由を特定できる表示はしない |
| ⑯ | 読み込み中 | 投稿詳細のレイアウトに沿ったスケルトン表示 |
| ⑰ | API取得エラー | 通信・サーバーエラーは専用メッセージ＋「再試行する」。再試行中はスケルトン |
| ⑱ | 戻るボタン | 開いた元の画面へ戻り、タイムラインならタブ・スクロール位置・取得済み投稿を復元 |
| ⑲ | PC・スマホ幅 | PCは中央配置で最大幅600px。スマホは画面幅に追従し適切な左右余白 |
| ⑳ | 最終ワイヤーフレーム | PC・スマホの最終案を承認済み |

## 5. 画面内の操作

### 5.1 投稿者・書籍

- ユーザー名 → 投稿者のプロフィール。自分の名前なら自分のプロフィール。
- 書籍表紙またはタイトル → 対象の書籍詳細。
- 表紙の画像がない、または読み込めない場合 → タイムラインと同じ `NO COVER` 代替表示。
- 著者・ジャンルは投稿詳細の書籍情報欄に表示しない。

### 5.2 おすすめ度・おすすめ理由・日付

- おすすめ度は `★` と `☆` による5つ星表示。`4/5` などの数値は併記しない。
- おすすめ理由は「続きを読む」なしで全文表示。独立したスクロール枠は設けない。
- 投稿日は年月日のみ（例: `2026/10/20`）。

### 5.3 いいね

- ハートと件数を一体のタップ・クリック領域とする。
- 未いいね: `♡ 12`、いいね済み: `♥ 13`。0件は `♡` のみ（`0` を出さない）。
- 他ユーザーの公開投稿に対し、いいね・取り消しができる。
- **自分の投稿にはいいねできない**（UIとAPI双方で制限）。
- 楽観的更新: 操作直後に見た目と件数を更新し、API失敗時は元の状態に戻す。
- API応答待ちの間は連続操作を防止する。
- タイムラインに戻った際は変更後のいいね状態を反映する。

### 5.4 本人専用メニュー

```text
投稿詳細の右上「…」
      │
      ├── 編集する → 専用「投稿編集」画面
      │
      └── 削除する → 削除確認ダイアログ
```

- 投稿者本人にのみメニューを表示する。
- 他ユーザーがURLやAPIを直接操作しても編集・削除できないよう、バックエンドで投稿所有者を検証する。

## 6. 投稿編集との連携

```text
投稿詳細（本人）
    │
    └─ … → 編集する
               │
               ▼
        専用「投稿編集」画面
        ・既存内容を初期表示
        ・おすすめ度
        ・おすすめ理由
        ・公開 / 非公開
               │
               └─ 保存成功 → 投稿詳細（最新内容）
```

- 公開状態ラベルは投稿詳細では変更不可。編集画面で変更する。
- 公開から非公開に変更した投稿は、取得済みの公開タイムライン一覧から除外する。
- **編集画面の詳細な入力UI、バリデーション、未保存変更の扱いなどは別仕様（`post-edit.md`）で設計する。** 上図の入力項目は今回の画面設計から想定される連携範囲を示す。

## 7. 投稿削除

### 7.1 確認ダイアログ

```text
┌──────────────────────────────┐
│                              │
│      投稿を削除しますか？    │
│                              │
│ この操作は取り消せません。   │
│                              │
│ [キャンセル]  [削除する]     │
│                              │
└──────────────────────────────┘
```

- 「キャンセル」ではダイアログを閉じるだけで、削除APIを実行しない。
- 「削除する」を最終確認したときだけ削除APIを実行する。
- 処理中は二重送信を防ぐ。
- 失敗時はエラーを示し、投稿詳細を維持する。
- 成功時は**投稿詳細を開いた元の画面**へ戻り、削除済み投稿を一覧から取り除く。
- タイムラインに戻る場合は、元のタブ・スクロール位置を維持し、一覧全体の再取得を必須としない。

## 8. 閲覧権限・非公開投稿

| 投稿状態 | 投稿者本人 | 他ユーザー |
|---|---|---|
| 公開 | 閲覧・編集・削除可 | 閲覧可、編集・削除不可 |
| 非公開 | 閲覧・編集・削除可 | 閲覧不可 |

- 非公開投稿は「新着投稿」「フォロー中」の公開タイムラインに掲載しない。
- 非公開投稿を本人以外が詳細取得しようとした場合、原則 `404 Not Found` を返し、存在の有無を推測させない。
- UIの非表示だけでは不十分。**API側でも閲覧権限と所有者権限を検証する**。
- 公開投稿の閲覧に必要な認証条件など、具体的なAPI契約は別途確認する。

- 「再試行する」で詳細取得を再実行し、再試行中はスケルトンを表示。
- 再失敗時も再試行可能。戻るボタンも使用可能。
- 404の状態と通信・サーバーエラーを混同しない。

## 10. ナビゲーションと状態復元

```text
タイムライン（タブ・スクロール・取得済み投稿）
      │
      └─ 投稿を選択 → 投稿詳細 ─「← 戻る」→ 元の状態を復元

ユーザープロフィール等
      │
      └─ 投稿を選択 → 投稿詳細 ─「← 戻る」→ 元の画面

直接URLで投稿詳細へアクセス
      │
      └─ 「← 戻る」→ タイムライン「新着投稿」

本人が投稿を削除
      │
      └─ 削除成功 → 元の画面へ戻り、一覧から対象投稿を除外
```

- 編集画面から保存して投稿詳細へ戻っても、投稿詳細の「戻る」は当初の遷移元へ戻る。
- タイムラインの既定の状態復元ルールと整合させる。

## 11. レスポンシブ・表示ルール

- PC: コンテンツ最大幅 **600px**、中央寄せ。
- スマホ: ビューポート幅に追従し、適切な左右余白を設ける。
- 投稿理由は省略・内部スクロールなし。長文は自然に折り返す。
- PC・スマホとも横スクロールを避ける。
- 基本レイアウトはタイムライン投稿カードと統一する。

## 12. 実装時に守る境界・未決定事項

### この仕様書で確定していること

- 画面構成・表示情報・操作の導線・表示条件。
- いいねの基本動作と失敗時の復元。
- 本人のみ編集・削除可能、非公開は本人のみ閲覧可能。
- 404／取得エラー／ローディングの表示。
- 戻る先とタイムライン状態復元。

### この仕様書だけでは確定していないこと

- 投稿編集画面の詳細なフォーム構成、入力制限、キャンセル・未保存変更の確認。
- 具体的なAPIパス、HTTPメソッド、リクエスト／レスポンスのスキーマ、認証方式の詳細。
- 投稿詳細へのルーティングURL形式、キャッシュの実装方式、データ取得ライブラリ。
- いいねAPI・編集API・削除APIが現時点で実装済みかどうか。
- 404以外の認証切れなど、全HTTPステータスごとの詳細な画面仕様。

**Codexへの指示:** 未決定事項を独断で「確定仕様」として扱わず、既存コードとAPIを調査して、必要な追加設計はユーザーへ一項目ずつ確認すること。既存の `timeline.md` が存在する場合は、共通デザインと状態復元の仕様を整合させること。
