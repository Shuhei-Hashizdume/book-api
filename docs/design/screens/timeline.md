# BookAPP タイムライン画面 仕様書

- 文書名: `timeline.md`
- 対象: タイムライン画面（新着投稿／フォロー中）
- 状態: 画面設計47項目確定
- 作成日: 2026-10-20
- 用途: Cursor / Codexへの実装指示・レビューの基準

> **実装上の原則**: 本書の「確定仕様」を優先する。未決定・要確認事項を推測で仕様確定しない。既存API・ORM・ルーティング・画面構成を実装前に確認し、差分を説明すること。

## 1. 目的と対象範囲

BookAPPは、読んだ本・学び・おすすめを記録し、他ユーザーの読了投稿から新しい本と出会えるアプリ。本画面では、公開された読了投稿を新着順に閲覧し、書籍詳細・投稿詳細・投稿者プロフィールへ移動し、他者の投稿にいいねできる。

**対象**: タイムラインの2タブ、投稿カード、一覧の取得・追加取得、いいね、画面遷移、状態表示、画面へ戻った際の復元。

**対象外（別画面で詳細設計）**: 投稿詳細画面そのものの全UI、書籍詳細画面、プロフィール画面、投稿編集画面の全UI、ユーザー検索機能。ユーザー検索機能は採用しない。

## 2. 画面構成とデータの表示条件

### 2.1 タブ

| タブ | 対象投稿 | 表示順 |
|---|---|---|
| 新着投稿 | 全ユーザーの公開読了投稿。**自分自身の公開投稿も含む** | `created_at DESC`、同日時は投稿ID降順 |
| フォロー中 | **自分がフォローしているユーザー**の公開読了投稿のみ | 同上 |

- 非公開投稿は両タブとも表示しない。
- 画面を**新しく開いた際の初期タブは「新着投稿」**。
- タブは横並び。選択中のタブは**下線**で示し、文字も太字にする。
- タブ領域は投稿一覧をスクロールしても画面上部に固定する（`sticky`相当）。固定ヘッダーがある場合は重ならないようにする。
- タブを切り替えると**切り替え先一覧のスクロール位置は先頭**にする。
- 同一のタイムライン画面内ではタブごとに取得済み投稿をキャッシュし、**既に開いたタブへ戻るだけでは再取得しない**。初めて開くタブは取得する。
- 画面を新しく開く場合、および明示的な更新操作では再取得する。

### 2.2 投稿カードの構成

上から以下を配置する。

1. 投稿者ユーザー名（最大1行、省略記号あり）と投稿作成日（右側、`YYYY/MM/DD`）。ユーザー名の全文はプロフィールで確認できる。
2. 書籍表紙（**56×80px**）と書籍タイトル（右側、**最大2行**、超過時は省略記号）。著者名は**カードには表示しない**。
3. おすすめ度（星1〜5の評価表示）。
4. おすすめ理由（**最大3行**、超過時は省略記号）。全文は投稿詳細で確認する。
5. いいねボタンと「続きを読む」導線。

カードはPC・スマホとも縦1列。PCのカード最大幅は**600px**、中央寄せ。スマホは利用可能幅に合わせる。カード間隔は**16px**。カード背景は白系、薄いグレーの枠線と角丸。目立つ影は付けない。

表紙画像がない／取得に失敗した場合は同じ**56×80px**の「NO COVER」共通代替表示を使用する。代替表示を押しても書籍詳細へ移動できる。画像は縦横比を不自然に引き伸ばさない。

### 2.3 操作領域

| 操作対象 | 動作 |
|---|---|
| 投稿者ユーザー名 | 投稿者のプロフィールへ移動。フォロー／解除はプロフィール側で実施 |
| 書籍表紙・書籍タイトル | 書籍詳細へ移動 |
| 投稿カードの本文領域／「続きを読む」 | 投稿詳細へ移動。おすすめ理由の全文を表示 |
| ハートといいね数 | **一体のボタン**としていいね／解除を切り替える。投稿詳細には移動しない |

- カードにフォローボタンは置かない。
- カードに投稿編集／削除ボタンは置かない。自分の投稿の編集・削除は投稿詳細画面で行う（削除時は確認が必要）。他人の投稿詳細に編集・削除を表示しない。
- カード内部のリンクやいいねボタンを押した場合、親カードの投稿詳細遷移を発火させない。

## 5. いいねの仕様

- 0件なら `♡` のみ。1件以上なら `♡ 12` のように件数を併記する。
- 自分がいいね済みなら塗りつぶした `♥ 12` のように表示する。
- ハートと件数は1つのボタンで、どちらを押しても同じ操作。
- **自分自身の投稿にはいいねできない**。ハート・件数は表示するが操作不可。サーバー側でも禁止する。
- いいね操作は**楽観的更新**：押した直後にハートと件数を更新し、APIが失敗したら元に戻してエラーを通知する。
- API処理中の連打・重複送信を防止する。
- いいね操作によって投稿詳細画面へ移動しない。
- いいねしたユーザー一覧への遷移は設けない（数字もいいねボタンの一部）。

## 6. 一覧取得・ページネーション・更新

### 6.1 取得単位

- 各タブとも**初回10件**。
- 一覧下部へ近づくと**次の10件**を自動取得する無限スクロール。
- 追加取得中は重複リクエストしない。
- 続きがなくなったら取得を停止する。
- 全件読み終えても「すべて表示しました」等の末尾メッセージや「もっと見る」ボタンは出さない。

### 6.2 カーソル方式（㊷確定）

- **OFFSETではなくカーソルページネーション**を採用する。
- 並び順は`created_at DESC`、同日時なら投稿ID降順。
- 最後に取得した投稿の`created_at`と投稿IDを基準に、**その投稿より後ろ（古い側）**の10件を取得する。
- 例：`(created_at < cursor_created_at) OR (created_at = cursor_created_at AND post_id < cursor_post_id)`。実際のORM属性名・DBの型は実装時に確認。
- APIは次ページ取得用カーソル（またはそれと等価な情報）と続きの有無をクライアントに伝えられる設計にする。
- カーソルの具体的なエンコード形式・レスポンスのフィールド名は**未決定**。
- 並び順を安定させても、閲覧中に削除・非公開変更・フォロー状態変更などがあれば一覧内容は変わり得る。新規投稿の挿入によるOFFSET方式特有のずれを避ける目的でカーソル方式を採用する。

### 6.3 更新のタイミング

- タイムライン画面を**新しく開く**際は最新を取得し、初期タブは「新着投稿」。
- スマホでは**プル・トゥ・リフレッシュ**で更新できる。
- PCはブラウザ再読み込みや画面の開き直しで更新する。
- 閲覧中の定期ポーリング・新着投稿の自動追加・「新しい投稿があります」通知は**採用しない**。
- 同一画面でのタブ再選択はキャッシュを使い、不要な再取得をしない。

## 7. 画面遷移と状態の復元

```text
                          ┌───────────────┐
                          │ タイムライン  │
                          │ 新着/フォロー │
                          └──────┬────────┘
                  ┌──────────────┼────────────────┐
                  ▼              ▼                ▼
              投稿詳細        書籍詳細        プロフィール
                  │              │                │
                  └──────────────┼────────────────┘
                                 ▼ 戻る
                    元のタブ・スクロール位置
                    取得済み投稿一覧を復元
```

- 投稿詳細・書籍詳細・プロフィールの**いずれから戻っても**、遷移前のタブ・スクロール位置・取得済み投稿データを復元する。
- **戻る操作だけでは一覧APIを再取得しない**。
- この「詳細画面から戻る」と「タブを切り替える」は異なる操作。**タブ切り替え時は先頭へ**、**詳細画面から戻ると元の位置へ**。
- 新しくタイムラインを開いた場合は初期タブ「新着投稿」かつ最新取得。
- 画面遷移後の復元はブラウザ履歴／クライアントルーターの構造に合わせて実装する。具体的な状態管理手法は未決定。

## 8. 読み込み・空表示・エラー表示

| 状態 | 表示・動作 |
|---|---|
| 初回取得中 | **投稿カード型スケルトン**を表示。取得後に実カードへ置換 |
| 未取得タブへ初めて切替 | そのタブでスケルトン表示し、初回10件を取得 |
| 追加取得中 | 一覧末尾にスケルトンを表示。既存投稿は残す |
| 初回取得失敗 | エラー説明と「再試行」ボタン。再試行で失敗したリクエストを再送 |
| 追加取得失敗 | 取得済み投稿を残し、末尾にエラー説明と「再試行」ボタン |
| 新着投稿が0件 | 投稿がない旨の説明を表示 |
| フォロー中が0件 | 説明文と**「新着投稿を見る」**ボタン。押すと新着投稿タブへ切替 |
| 最終ページ取得済み | 追加取得停止。末尾メッセージは表示しない |
| 表紙画像なし・読み込み失敗 | 同寸法の**NO COVER**代替表示 |

**空表示例（フォロー中）**

```text

│  新着投稿       フォロー中   │
│                 ━━━━━━━      │
│                              │
│ フォロー中のユーザーの       │
│ 公開投稿はまだありません。   │
│                              │
│    [ 新着投稿を見る ]        │
└──────────────────────────────┘
```

- **ユーザー検索機能は設けない**。ユーザーとの出会いは「新着投稿 → ユーザー名 → プロフィール → フォロー」。

## 9. 投稿削除・公開状態変更時の整合性

### 9.1 自分の投稿を削除した場合

- 削除確認後、**削除API成功時のみ**該当投稿をタイムラインの取得済みデータから取り除く。
- 「新着投稿」「フォロー中」の両キャッシュに同一投稿があれば除去する。
- 一覧全体を再取得しない。元のタブ・スクロール位置は可能な限り維持する。
- API失敗時は一覧から除去しない。

### 9.2 自分の公開投稿を非公開へ変更した場合

- **変更API成功時のみ**該当投稿を両タブの取得済みデータから取り除く。
- DB上の投稿は残す。公開タイムラインからのみ消える。
- 一覧全体を再取得しない。元のタブ・スクロール位置は可能な限り維持する。
- API失敗時は公開状態・一覧を変更しない。

### 9.3 他ユーザーによる変更

- 他ユーザーが投稿を削除・非公開変更しても、閲覧中に自動ポーリングしない方針は維持する。
- 次回取得・明示更新時には公開条件を適用する。
- 古いキャッシュから非公開情報を取得できないよう、**投稿詳細API等でも認可・公開範囲の検証を必須**とする。
- 閲覧中の古いキャッシュとサーバーの状態が異なる場合の詳細エラー文言は要確認。

## 10. アクセシビリティ（㊻確定）

- Tabキーでタブ、ユーザー名、書籍表紙・タイトル、いいね、「続きを読む」、再試行等の操作対象へ移動可能。
- Enterキー等で各要素を操作可能。タブには適切なキーボード操作規則を採用する。
- フォーカス中の要素を視覚的に判別できる。
- いいねボタンには状態に応じた読み上げ名（例「いいねする」「いいねを解除する」）を設定。
- 選択中のタブを支援技術へ伝える。
- リンクにはリンク要素、ボタンにはボタン要素を用い、クリック可能な非セマンティック要素だけに依存しない。
- 操作不可の自分のいいねは、見た目と支援技術の双方に操作不可状態を伝える。
- PC・スマホ共通。

## 11. API・DBへの影響（実装前の確認事項を含む）

### 11.1 タイムラインAPI

会話内で確認済みとされた既存構成（**現行リポジトリの最新状態は未再確認**）：

- `GET /timeline/recommended`：公開投稿の一覧。
- `GET /timeline/following`：フォロー中ユーザーの公開投稿。
- `TimelinePostResponse`には投稿ID、ユーザーID、ユーザー名、書籍ID、書籍タイトル、おすすめ度、おすすめ理由、作成日時、表紙URL等があると報告されている。
- 既存APIはリスト返却で、カーソルページネーションといいね情報の追加が必要になる見込み。

**必要なAPI上の能力（フィールド名・URLは未確定）**:

1. 2タブの対象条件に応じた公開投稿の取得。
2. `created_at`＋投稿IDによる決定的な降順ソート。
3. `limit=10`相当の件数指定と、次ページカーソルの入出力。
4. 表示用のいいね数、およびログイン中ユーザーのいいね済み判定。
5. 自分の投稿か判定できる情報（既存の投稿者ID等で可）。
6. 読了投稿の公開・非公開状態をサーバーで適切にフィルタリング。
7. 他ユーザーの公開投稿詳細を表示できる読み取り経路（既存APIの確認が必要）。
8. いいね／解除APIの成功・失敗と、自分の投稿へのいいね禁止。

### 11.2 DB・ORM

- 読了投稿には`created_at`と投稿IDが必要（既存モデルを確認）。
- 公開フラグ`is_public`、投稿者ID、書籍ID、おすすめ度・理由、表紙参照の取得経路を確認。
- いいねの保存先テーブル、ユーザーと投稿の一意制約、集計方法を確認する。
- フォロー関係の保存先と対象判定を確認する。
- **本仕様だけを理由に新しいテーブルを必ず作るとは決めない**。既存スキーマとの差分を調査する。
- 書籍の著者名はタイムラインカードに不要。**著者表示のためだけのAPIフィールド追加は不要**。

### 11.3 実装上の注意

- カーソルの条件と`ORDER BY`の順序は一致させる。
- 公開判定はフロントの非表示処理だけに依存せず、サーバー側で適用する。
- タブキャッシュ・戻る操作時の復元・削除／非公開時のキャッシュ無効化の責務を整理する。
- いいねはサーバー側で本人投稿禁止を強制し、フロントの操作不可表示だけに頼らない。
- APIを変更する場合、既存の呼び出し元・テストへの影響を確認する。

## 12. テスト観点（受け入れ条件）

- [ ] 新着投稿に自分を含む全ユーザーの公開投稿が表示される。
- [ ] フォロー中にはフォロー先の公開投稿だけが表示される。
- [ ] 非公開投稿は両タブに表示されない。
- [ ] 投稿作成日時降順、同日時は投稿ID降順になる。
- [ ] 投稿者名1行、タイトル2行、理由3行の省略表示が機能する。
- [ ] 日付が`YYYY/MM/DD`で表示され、著者名はカードに出ない。
- [ ] 表紙56×80px、欠損時NO COVER、PC最大幅600px、カード間16px。
- [ ] 選択タブの下線と上部固定が機能する。

### 操作・遷移

- [ ] ユーザー名→プロフィール、表紙・タイトル→書籍詳細、本文・続きを読む→投稿詳細。
