# BookAPP 共通認証フロー設計

作成日：2026-10-19  
更新日：2026-10-20  
状態：画面間の認証・遷移・復帰先解除・基本的なエラー処理は確定。Cookie認証は将来設計であり未実装。識別方法・配備構成に依存する項目は未決定。

## 1. 目的・適用範囲・設計書の役割

本書はBookAPPのウェルカム、ログイン、新規登録、ホーム、認証必須画面に共通する認証フローを定義する。各画面の固有の表示・入力検証・ワイヤーフレームは画面別設計書を正本とし、本書は認証状態、API、画面間遷移、復帰先、期限切れ、ログアウト、セキュリティを扱う。

- ホームは一つの画面であり、ゲストとログイン済みで表示内容が変わる。「ゲスト用ホーム」「ログイン済みホーム」は別々のURLや別画面を意味しない。
- ゲストも公開投稿など認証不要の範囲を閲覧できる。本棚・気づき・マイページなど認証必須の操作にはログインが必要。
- 保護画面へのアクセスを契機に認証した場合は、認証成功後に**元々アクセスしようとした画面**へ移動する。
- ログイン画面または新規登録画面の「← 戻る」を押した場合は、ウェルカムへ移動し、保持していた保護画面への復帰予定を解除する（A案、確定）。
- 本書は設計仕様であり、以下の「将来設計」は現行バックエンドに実装済みであることを意味しない。

関連：[ウェルカム](../screens/welcome.md)／[ログイン](../screens/login.md)／[新規登録](../screens/signup.md)／[ホーム](../screens/home.md)。

## 2. 現行バックエンドのAPI契約と将来の変更

以下は既存APIに関する確認済みの設計前提。現行契約と将来のCookie方式を混同しない。

| API | 現行契約 | 将来設計との差分 |
|---|---|---|
| `POST /users` | 認証不要。JSON `username`, `email`, `password`。成功201で `id`, `username` を返し、トークンは返さない | 登録成功後、別途ログインAPIを呼ぶ方針を維持 |
| `POST /users/login` | JSON `email`, `password`。成功200で `access_token`, `token_type: bearer`。認証失敗401、入力不正422 | サーバーがHttpOnly Cookieを設定する方式へ変更する必要がある |
| `GET /users/me` | `Authorization: Bearer <access_token>`。成功200で `id`, `username`、認証拒否401 | Cookieを用いた本人確認に対応させる必要がある |
| ログアウト | 専用APIは現行契約にない | Cookie削除を行うサーバー側処理を追加する必要がある |

- `DELETE /users/me` はアカウント削除であり、ログアウトAPIとして使用しない。
- 現行JWTは署名・有効期限・ユーザー識別情報・ユーザー存在などの検証対象。**将来設計の7日間と現行トークンの有効期限が一致するとは限らない**。
- 現行コードにCookie設定、Cookie認証、Origin検証、ログアウト用の専用エンドポイントが実装済みとは扱わない。
- フロントエンドURL、Cookie方式への移行時のAPI契約の詳細、レスポンスの扱いは未決定。

## 3. 認証情報・有効期限の方針

将来の認証方式として、サーバーが発行したJWTを**HttpOnly Cookie**で保持する。HttpOnlyとはJavaScriptからCookieの値を直接読み取れない属性を指す。

| 項目 | 確定した方針 |
|---|---|
| 保存先 | 将来はHttpOnly Cookie。現行はBearer JWT |
| 本番Cookie | `Secure=true`、`SameSite=Lax`、`HttpOnly=true` |
| 認証の有効期間 | ログイン時から固定7日（604,800秒） |
| 有効期間の延長 | APIアクセスだけでは延長しない（スライディング更新なし） |
| 再ログイン | 新たな認証が成功した時点から新しい7日間を設定 |
| 認証確認 | `GET /users/me` を利用。Cookieの有無をJavaScriptで調べて省略しない |

- Cookie名、`Path`、`Domain`、開発環境での属性、JWTとCookieの厳密な失効タイミング、Bearerからの移行手順は未決定。
- 期限切れ・ログアウト後に、本人情報を認証済みとして表示し続けない。
- パスワードやJWTをURL、ログ、永続的なブラウザストレージへ残さない方針とする。

## 4. 共通の認証確認と表示

ウェルカム、ログイン、新規登録、および認証状態を必要とする画面では、必要なタイミングで `GET /users/me` により本人確認を行う。

```text
画面に入る／認証状態の確認が必要
             |
             v
       GET /users/me
             |
     +-------+------------------+
     |       |                  |
   200      401          通信失敗・5xx等
     |       |                  |
 認証済み  未認証扱い        確認不能
     |       |                  |
 画面別の   画面別の        共通エラー表示
 遷移・表示 遷移・表示       「再試行する」
```

- 認証確認中は、ログイン済み利用者だけが見られるデータや、ログイン・新規登録フォームを先に表示・操作させない。
- 共通ローディング文言は `BookAPP` と `読み込み中...`。
- 確認不能時は `ログイン状態を確認できませんでした。` と `再試行する` を表示する。通信障害、タイムアウト、5xx等を401と混同せず、ゲストと断定しない。
- `再試行する` は本人確認を再実行する。登録やログインのPOSTを自動的に再送信しない。
- **401だけでは「初めてのゲスト」と「以前の認証が期限切れ」を確実には区別できない。** 区別の具体的な方法は未決定。
- 期限切れと識別できた場合はログイン画面で `ログインの有効期限が切れました。もう一度ログインしてください。` と表示する。識別できない401に期限切れ通知を断定表示しない。

## 5. ログイン・新規登録の共通処理

### 5.1 ログイン

1. ログイン画面の表示時に `GET /users/me` で確認する。200ならフォームを表示せず第6節の遷移規則に従う。未認証ならフォームを表示する。
2. `email` と `password` を検証する。欄を離れたとき（blur）はその欄、送信時は全欄を検証し、入力不正ならAPIを呼ばない。
3. `POST /users/login` を実行する。送信中は `ログイン中...` とし、クリック・Enterによる二重送信を防ぐ。送信時にはパスワードを伏字へ戻す。
4. 成功したら認証状態を反映し、第6節の遷移規則に従う。
5. ログインAPIの401では `メールアドレスまたはパスワードが正しくありません。` と表示し、メールアドレスを保持、パスワードを消去する。入力不正422は該当欄に表示する。
6. 通信失敗・15秒タイムアウトでは `通信エラーが発生しました。時間をおいて再度お試しください。` と表示し、両入力値を保持する。サーバー側でログイン済みとなっている可能性を排除せず、自動再送信しない。

ログイン時のパスワードは1〜128文字を受け付ける。**登録時の8文字以上という制約をログインに追加しない。** 詳細は `login.md` を参照する。

### 5.2 新規登録と自動ログイン

1. 新規登録画面の表示時に `GET /users/me` で確認する。200なら第6節の遷移規則に従う。
2. `username`（1〜50文字、空白不可）、`email`（有効形式、255文字以下）、`password`（8〜128文字）を検証する。
3. `POST /users` を送信する。成功201を受け取った時点で登録完了とする。登録ボタンは `登録中...` とし、二重送信を防ぐ。
4. 登録時のメールアドレスとパスワードで `POST /users/login` を呼び、自動ログインする。自動ログイン中も `登録中...` を維持する。
5. 自動ログイン成功後は第6節の遷移規則に従う。
6. 登録201後に自動ログインが失敗した場合、登録完了を取り消さず、`アカウントの登録は完了しました。自動ログインできなかったため、ログインしてください。` とログイン画面への案内を表示する。**同じ登録操作で再登録させない。** ログイン画面へ進む際は復帰先を引き継ぐ。

- 登録APIの409では `ユーザー名またはメールアドレスが既に登録されています。` と表示し、どちらが重複したか断定しない。
- 登録APIの422は対応する入力欄へ表示する。
- **登録APIの送信後、成功201を受け取る前に通信失敗・タイムアウトとなった場合**は登録成否不明とし、`登録結果を確認できませんでした。登録が完了している可能性があります。` と表示する。`もう一度登録する` と `ログイン画面へ` を提示し、自動再送信はしない。入力値は保持し、パスワードは伏字とする。
- 利用者が明示的に `もう一度登録する` を選んだ場合に限り、再検証のうえ登録を再送信できる。
- 201後の自動ログイン失敗と、201を受け取っていない登録成否不明は別状態として扱う。

### 5.3 タイムアウト・重複処理

- `POST /users/login` と `POST /users` は**各リクエストごとに15秒**のクライアント側タイムアウトを設ける。登録＋自動ログインを合計15秒に制限する意味ではない。
- タイムアウトや通信中断はサーバー処理の中止を保証しない。
- 重複クリック・Enter・遅延応答によって、同じ操作が複数回実行されたり、古い応答が新しい試行の表示を上書きしたりしないようにする。具体的な実装方法は未決定。

## 6. 認証成功後の遷移・復帰先・「戻る」（確定）

### 6.1 基本ルール

| 認証を始めた経緯 | 認証成功後の行き先 |
|---|---|
| ウェルカムからログイン | ホーム |
| ウェルカムから新規登録 → 自動ログイン | ホーム |
| ログイン・新規登録への直接アクセス（有効な復帰先なし） | ホーム |
| ゲストが本棚など保護画面を要求 → ログイン | 元々要求した保護画面 |
| ゲストが本棚など保護画面を要求 → 新規登録 → 自動ログイン | 元々要求した保護画面 |
| 登録201後、自動ログイン失敗 → ログイン画面で認証成功 | 復帰先が保持されていれば元々要求した保護画面 |
| ログイン・新規登録画面で既に認証済みと判定 | 有効な復帰先があればその画面、なければホーム |

```text
【保護画面から認証した場合】
ゲスト用ホーム → 本棚を選択 → ログイン必要案内
                                  |
                     +------------+-------------+
                     |                          |
                  ログイン                    新規登録
                     |                          |
                 認証成功                登録 → 自動ログイン
                     |                          |
                     +------------+-------------+
                                  |
                                  v
                             元の本棚画面

【ウェルカムから認証した場合】
ウェルカム → ログイン／新規登録 → 認証成功 → ホーム
```

### 6.2 復帰先の引き継ぎ

- 保護画面を要求した時点で、その**アプリ内の目的画面**を復帰先として扱う。
- ログイン必要案内からログインまたは新規登録へ進んでも、復帰先を保持する。
- ログイン画面の `新規登録` リンク、新規登録画面の `ログイン` リンクで認証手段を切り替えた場合も、復帰先を引き継ぐ。
- 登録成功後の自動ログインが失敗し、手動ログインへ進む場合も、復帰先を引き継ぐ。
- 復帰先がない、無効、または利用できない場合の基本的な行き先はホーム。ただし個別の権限不足や対象削除などの表示は別途設計する。
- 外部サイトのURLを無条件に復帰先として受け付けない。許可されたアプリ内の画面だけを遷移先とする。保存方式・許可リストの具体化・履歴制御は未決定。

### 6.3 「← 戻る」による復帰先解除：A案

**ログイン画面と新規登録画面の両方で、左上の `← 戻る` は必ずウェルカムへ移動し、復帰先を解除する。** ブラウザの閲覧履歴には依存しない。

```text
本棚を開こうとする
       |
       v
   ログイン画面／新規登録画面
       |
       +-- 認証成功 --------------------> 本棚
       |
       +-- 「← 戻る」
                 |
                 v
             ウェルカム
           （本棚への復帰予定を解除）
                 |
                 v
           改めてログイン／登録
                 |
                 v
                ホーム
```

- 解除するのは認証後の**復帰先情報**であり、アカウントそのものを削除したり、ログアウトを実行したりする操作ではない。
- 画面下部の `ログイン`／`新規登録` リンクによる認証手段の切替は「← 戻る」とは異なり、復帰先を解除しない。
- ログイン・新規登録画面からの通常のブラウザバックやタブ終了、ページ再読み込み時の復帰先の扱いは未決定。確定している解除操作は画面内の `← 戻る`。

## 7. 認証期限切れ・再ログイン

- 保護画面の操作時などに認証失効が判明したら、本人専用データを認証済みとして扱わず、ログインを求める。
- 期限切れと**識別できた場合のみ**、ログイン画面上部に `ログインの有効期限が切れました。もう一度ログインしてください。` を表示する。
- 保護画面へのアクセスを契機とする再ログインでは、第6節に従い元の目的画面を復帰先として扱う。ウェルカムからのログインはホームへ進む。
- 再ログイン後の入力途中データの復元は確定していない。**画面への復帰**と**入力内容の復元**は別仕様。
- 現行の401だけで初回ゲスト／期限切れを識別する方法は未決定。識別方式が定まるまで、期限切れを断定する実装を前提にしない。

## 8. ログアウト

- ログイン済みのヘッダーのユーザー名メニューから `ログアウト` を選択する。確認ダイアログは表示しない。
- 将来のCookie認証では、サーバー側で認証Cookieを削除する処理が必要。現行には専用ログアウトAPIがない。
- ログアウト成功時は認証済み状態・本人専用キャッシュ等を破棄し、ウェルカムへ移動する。古い復帰先を次回ログインへ持ち越さない。
- ログアウト失敗時はログアウト済みと断定せず、元の画面に留まり `ログアウトできませんでした。通信状況を確認して、もう一度お試しください。` と表示する。
- Cookie削除とサーバー側JWTの失効・即時無効化は同義ではない。JWT失効管理の追加要否は未決定。

```text
ログイン済みホーム
      |
      v
ユーザー名 ▼ → ログアウト
      |
      +-- 成功 → 本人情報の破棄 → ウェルカム
      |
      +-- 失敗 → 元画面に留まる → エラー通知
```

## 9. セキュリティと通信の共通方針

- 本番Cookieは `HttpOnly`・`Secure`・`SameSite=Lax` とする。`SameSite=Lax` のみで全てのCSRF対策が完了するとみなさない。
- **CSRF（クロスサイトリクエストフォージェリ）**：利用者の認証状態を悪用し、別サイトなどから意図しない操作を送らせる攻撃。Cookie方式への移行に合わせ、状態変更リクエストでのOrigin検証を採用する方針とする。
- Origin検証の適用範囲、許可Origin、プロキシ配下の扱い、CORS設定、CSRFトークンの追加要否は実際の配備構成に合わせて確定する。Origin検証が現行実装済みであるとは扱わない。
- 認証・登録APIのエラーで、メールアドレスやアカウントの存在を必要以上に断定しない。ログイン401は資格情報のどちらが不正かを区別しない文言を使用する。
- 認証後の復帰先はアプリ内の許可された画面に限定し、外部URL等への無条件リダイレクトを禁止する。
- 未認証状態で本人情報を先行表示しない。ログアウト後は本人専用の表示・キャッシュを残さない。
- 具体的なHTTPヘッダー、Cookie名、フロントエンド・API間の通信条件は実装前に確定する。
